# Renewable microgrid dispatch ledger

The `total_unserved_MWh` summary is the sum of `unserved_MW` over all one-hour periods.

Implement `/app/microgrid.py` and make it executable through:

```text
python3 /app/microgrid.py INPUT.json OUTPUT.json
```

The input is UTF-8 JSON. Reject duplicate object member names at any depth. The top-level object must contain exactly `horizon_hours`, `reserve_MW`, `generators`, `storage`, and `periods`; each period, generator, and storage object must contain exactly the fields listed here. `horizon_hours` must be a JSON integer from 1 through 96, `generators` must contain at least one unit, and `periods` must contain exactly `horizon_hours` records. JSON booleans are not numbers or integers. `reserve_MW` is a nonnegative spinning-reserve requirement applied in every hour. Each period has `load_MW` and `renewable_MW`. A generator has `id`, `min_MW`, `max_MW`, `marginal_cost`, `startup_cost`, `ramp_up_MW`, `ramp_down_MW`, `min_up_hours`, `min_down_hours`, and `initial_state` (`on` or `off`). The storage object has `capacity_MWh`, `initial_MWh`, `max_charge_MW`, `max_discharge_MW`, `charge_efficiency`, and `discharge_efficiency`.

Each storage efficiency must be greater than zero and at most one.

A generator that is off must have `power_MW` equal to zero. Every reported storage `state_MWh` must be between zero and `capacity_MWh`, inclusive. The dispatch policy below is fixed; the reserve requirement validates its result and does not change the policy or merit order. For reserve accounting, an online generator contributes `min(max_MW - power_MW, ramp_up_MW)` MW of upward reserve; an offline generator contributes zero. Storage contributes `min(max_discharge_MW - discharge_MW, state_MWh * discharge_efficiency)` MW. For each online generator in turn, treat that unit as unavailable and sum the remaining online-generator reserve plus storage reserve. `available_MW` is the minimum across those single-generator outage cases. If no generator is online, `available_MW` is storage reserve alone and `limiting_outage_id` is `null`. Reject the complete input atomically if any hour's available reserve is more than `1e-9` MW below `reserve_MW`.

Return one UTF-8 JSON object with exactly two top-level keys, in this order: `dispatch`, then `summary`. Each `dispatch` item is one hour in input order and has exactly these keys in this order: `generators`, `storage`, `reserve`, `renewable_used_MW`, `curtailment_MW`, `unserved_MW`, `balance_residual_MW`. `generators` is an input-order array of objects with exactly `id`, `on`, and `power_MW`. `storage` is an object with exactly `charge_MW`, `discharge_MW`, and `state_MWh`. `reserve` is an object with exactly `required_MW`, `available_MW`, and `limiting_outage_id`; the last value is the lexicographically smallest ID among tied limiting online-unit outages, or `null` when no generator is online. The `summary` object has exactly these keys in this order: `total_cost`, `total_unserved_MWh`, `total_renewable_curtailment_MWh`, `final_storage_MWh`, and `commitment_hours`; the last field maps each input generator ID to its number of committed hours. All numeric output values are JSON numbers and `on` is a JSON boolean.

`renewable_used_MW` is renewable power used for load plus renewable power stored; it excludes thermal power stored. `charge_MW` is total power entering storage from renewable and thermal surplus. For each hour the balance is `renewable_used_MW + sum(generator power_MW) + discharge_MW - charge_MW + unserved_MW = load_MW + balance_residual_MW`. Storage state advances by `charge_MW * charge_efficiency - discharge_MW / discharge_efficiency` over each one-hour period. The `total_cost` summary is exactly the sum over all hours of each generator's `power_MW * marginal_cost`, startup costs for off-to-on transitions, and `unserved_MW * 10000.0`; renewable curtailment has no cost. This cost is a reported ledger value, not a dispatch optimization objective.

The initial state is the state at the start of the first hour, with zero elapsed time in that state. Apply the minimum up/down duration from that point, including the first hour. When a unit changes commitment in hour t, that hour counts as the first hour in its new state; keep that state for the remaining required hours. Each hourly commitment must also respect its ramp limits. Units that must stay on because of their minimum up time or ramp-down limit remain committed, but commitment alone does not require preserving the previous hour's power. First reserve each must-run unit at its minimum feasible output for the hour: the greater of min_MW and its ramp-down floor when previously on. Then allocate the remaining deficit in merit order by (marginal_cost, id) across all already-on and startable units, including must-run units that have room to increase. When no must-run obligation remains and the remaining deficit is zero, leave the unit off rather than retaining an idle commitment. Do not start a unit whose minimum feasible output exceeds the remaining deficit. Report startup cost once when a unit changes from off to on; total cost is marginal generation cost plus startup cost plus the unserved-load penalty, not an optimization objective.

For each hour, renewable energy serves load first. Use remaining renewable surplus to charge storage within its power and energy limits, then curtail any unused renewable energy. When renewable supply is insufficient, dispatch feasible thermal output in merit order, then discharge available storage within its power and energy limits, and record any remaining deficit as unserved load. A must-run thermal minimum that exceeds the deficit may be absorbed by available storage charging capacity; if the resulting surplus cannot be absorbed while satisfying the storage limits, reject the input as infeasible and preserve the output path. Do not report negative charge, discharge, unserved load, or storage energy. Preserve input order in the result and use deterministic tie handling.

Reject malformed, non-finite, negative, inconsistent, or horizon-violating inputs with a nonzero exit and leave `OUTPUT.json` absent or byte-for-byte unchanged. Validate the complete record before publishing any output. Numeric fields must be finite; residual magnitude must be at most `1e-9` MW and storage state at most `1e-9` MWh from the stated recurrence. Re-running the same valid input must be idempotent and produce the same JSON bytes; an invalid run must not leave a temporary file beside the destination. The implementation must handle newly constructed valid systems, not a single fixture.
